## 2. ID：数值上限只是第一道检查

本包曾出现有符号长整数解析溢出、游戏重生成 ID 的故障。新 ID 统一采用 **16 位大写十六进制，范围 `0000000000000001` 至 `7FFFFFFFFFFFFFFF`**。不要生成 0（通常有空引用语义）；不要使用 `FFFFFFFFFFFFFFFF`。

该规则适用于章节、章节组、任务、任务目标、奖励及链接对象等定义。依赖、章节组、奖励表、`linked_quest` 等字段是引用，不可当成新定义随机改写。

```python
# 示例规则；实际分配还要查全库冲突并持久化映射。
candidate = f"{rng.randrange(1, 1 << 63):016X}"
assert 0 < int(candidate, 16) <= 0x7FFFFFFFFFFFFFFF
assert candidate not in used_ids
```

扫描必须包含所有相关 `.snbt`，包括章节组和奖励表。只匹配恰好 16 位的正则会漏掉本来就写错长度的 ID；应先提取所有 `id` 字段，再检验格式/范围。

## 3. 保留进度靠稳定对象映射

**固定随机种子不等于稳定 ID。** 插入任务、添加一个目标或奖励、改变随机调用次数，都可能让后续对象整体换号。

应维护稳定的 `业务 key → 章节/任务/目标/奖励 ID` 映射；改标题、翻译或位置不会改变 key。分配新 ID 前先预留全部既有 ID。旧 ID 冲突要报错停下，不能悄悄给已发布对象换号。

验收必须逐项比较“同一个业务任务的 ID 是否没变”，不能只检查“旧 ID 还出现在文件里”。后者发现不了把旧压缩机 ID 分配给新电路任务的错误。

### 当前 MEK 生成器仍有的问题（2026-09-25 只读确认）

`build_mek_chapter.py:load_previous_ids()` 仍按现有文件前 11 个块与 `OLD_KEY_ORDER` 对齐，没有从文件读取稳定业务 key。当前 58 任务文件已在旧任务中间插入精英/终极电路，下一次读取会得到：

| key | 当前函数读到的 ID | 应保持的原任务 ID |
|---|---|---|
| compressor | `163A0C94E5113468`（精英电路） | `3596905358881BEE` |
| separator | `2E78DFC45939175D`（终极电路） | `7AD5A85F7DD61709` |

**因此不要在生产目录直接重跑这个生成器。** 当前生成后的章节和生成器安全性是两件事；当前旧 ID 归属正常，不代表第二次运行也安全。后续应改为持久化完整映射，给全部 58 个任务及其子对象建立稳定标识，并在临时输出上验证两次运行结果一致。

另外，当前脚本先写文件再做部分校验；括号切块未处理字符串/注释；依赖检查不是完整的任务图检查。这些是待修复项，不能将其自检当成正式 SNBT 解析器。

## 4. SNBT 结构和依赖

- 章节必须有正确的 `filename`、`id`、`title`、`group` 与排序字段；不要漏章节标题。
- 每个任务至少有一个有效目标；多个目标必须全部输出到 `tasks` 数组。历史上太空生成器遗漏多任务分支，导致部分任务没有目标。
- `dependencies` 必须指向任务 ID，不能指向目标或奖励 ID。向前搜索最近的 `id` 很容易误取子对象。
- 检查悬空、自依赖和环；还要人工检查是否用高级机器锁住了其自身原料。
- `quest_links` 是独立对象结构；不要用简单字符串切片把 `linked_quest` 切空。未使用时保留合法空数组即可。
- SNBT 支持数值后缀（如任务数量 `8L`、坐标 `2.5d`）。字符串中的括号不是结构括号；仅计算 `{}` 数量不足以验证文件。
- 游戏重存可能改变字段顺序、缩进及数组排版。比较结构与语义，而不是将每一处文本差异都当成任务变化。

## 5. 文本、目标、奖励与布局

**自 2026-09-17 起，新增或修改的自建任务文本一律内联中文。** 原 Sunlit Valley 章节保留原有语言键。历史翻译/资源包工具不是新增章节必须执行的步骤。

教程必须区分模组默认机制、本包配方改动和建议玩法。核对依据的优先顺序：当前实例最终配方/实际行为 → 当前 JAR 的数据与实现 → 对应版本源码 → 官方文档/教程。语言文件只提供命名线索，不证明物品已注册或配方可用。

特别注意：

- `item` 与 `block` ID 不可混用；模组更新后旧 ID 可能仍存在于语言文件。
- 标签的存在不等于非空；`forge:`、`c:` 和 `gtceu:` 不可凭名字互换。
- 电路标称 EV 并不证明它必须由 EV 机器生产；硬门槛要核对所有获取路线。
- Mek 气体/浆液与液体不能当成同一类型；不要用普通流体目标假装检测化学品。
- 合金、倍矿倍率、输入数量和装备燃料不能凭旧教程猜测。当前 MEK 扩写文本仍有需返工的机制描述，见 STATUS 待办。
- 奖励要与本包经济匹配，不应直接发放下一阶段关键机器/电路而绕过门槛。
- 多方块控制器/外壳的物品任务只证明拿到了材料，不证明结构形成、工作或安全运行。
- 检查坐标重复、线条交叉和主线顺序；游戏内打开任务书检查缩放与可读性。
- 大背景使用本版支持的章节 `images` 结构和可加载的资源路径，别凭其它版本教程添加未验证的 `background` 字段。

## 6. 必做验证流程

1. 先看 `git status`、相关历史和现有章节；识别游戏内改过的标题、坐标、依赖。
2. 在临时目录生成，保留原始章节与完整 ID 映射。生成前失败不应损坏原文件。
3. 用能处理本版 SNBT 的解析器检验；另外做 ID 范围/唯一性、任务类型、全库引用及无环检查。
4. 按业务 key 比较既有章节、任务、目标和奖励的 ID；核对多目标数量。
5. 对临时输出连续运行两次生成器，比较字节或规范化结构，确保幂等且不会吞掉人工编辑。
6. 核对任务中所有 item/icon/reward ID 的实际注册；检查外部前置是真正的任务 ID。
7. 在测试存档加载并打开章节；测试物品目标、前置解锁、奖励发放和服务端同步。
8. 测试成功后才覆盖正式章节，检查 Git diff，再制作包含生成器版本与部署说明的补丁包。

现有轻量检查脚本只完成其中一部分。`node --check` 不验证 SNBT；正则、括号计数、模拟 API 均不能代替第 7 步。
